# 内容发现入口合并设计（首页频道 × 分类 Tab）

- 日期：2026-11-01
- 状态：设计方案（未改代码）
- 涉及页面：首页排行榜、推荐本本、频道页、每周必看、分类 Tab、分类/标签详情

---

## 1. 现状：两条互不相干的发现路径

```
底部 Tab
├─ 首页
│   ├─ 关注 / 排行榜 / 随便看看
│   └─ 排行榜 Tab
│       ├─ [🔥 推荐本本]  → promote        （压入新路由）
│       ├─ [禁漫汉化组]    → channel/hangroup
│       ├─ [禁漫去码]      → channel/nomosaic
│       ├─ [全彩化]        → channel/coloring
│       └─ [每周必看]      → weekly
│
├─ 分类
│   ├─ 顶级分类 chips      → category/{id}
│   ├─ 子分类 chips        → category/{id}?sub=...
│   └─ 官方标签墙          → tag/{tag}
│
├─ 搜索
└─ 我的
```

问题不是「多了一个页面」，而是：

1. **同一类内容发现能力有两个前门**：首页频道行和分类 Tab 都能进入作品流，但入口、页面样式、返回行为各自独立。
2. **首页承担了不该承担的导航职责**：排行榜页本应只回答「现在什么最热」，却同时放了 5 个运营入口。
3. **层级不统一**：从首页点「推荐本本」是一层，从分类点「同人」也是一层，但它们互不连通，用户要先想清楚「该从哪个入口找」。
4. **实现重复**：分类详情、标签页、频道页都是「标题 + 排序 + 网格 + 分页」的同一套结构，却维护了三份代码。

---

## 2. 关键判断：合并入口与层级，不强行合并内容模型

这 6 类入口的数据模型并不一样：

| 入口 | 数据来源 | 展示模型 | 是否分页 |
|---|---|---|---|
| 顶级/子分类 | `/categories/filter?c=`、`/search?c=` | 网格 | 是 |
| 官方标签 | `/search?main_tag=3` | 网格 | 是 |
| 汉化组/去码/全彩化 | `/search?main_tag=0/3&search_query=` | 网格 | 是 |
| 推荐本本 | `/promote` | 多组横向卡片 | 否（运营编排） |
| 每周必看 | `/week` + `/week/filter` | 期数 chips + 网格 | 当前只取第 1 页 |

把 6 类入口全部塞进一个垂直滚动页里「内联展开」看似层级最少，但会带来：

- 同一页里混排网格与横向卡片，嵌套滚动；
- 多个数据源同时加载，首屏变慢；
- 分页状态互相干扰，长列表无法虚拟化；
- 空态/错误态难以统一。

**结论：合并「入口」和「详情层级」，但保留三种展示模型。**

---

## 3. 方案对比

| 方案 | 做法 | 层级 | 优点 | 缺点 |
|---|---|---|---|---|
| A. 只搬入口 | 把首页 5 个入口搬到分类 Tab，详情仍是独立路由 | 仍然多层 | 改动最小、风险最低 | 层级没收敛，只是换了个入口 |
| **B. 嵌套图 + 统一内容流（推荐）** | 分类 Tab 内做「发现中心」；分类/子分类/标签/频道共用同一个 Feed 页面；推荐/每周保留专用布局但归入同一嵌套图 | **2 层** | 底部 Tab 始终是分类；返回一致；代码去重；扩展新入口成本低 | 需要改路由结构和一个统一 ViewModel |
| C. 单页全内联 | 分类 Tab 一页内展开所有频道/推荐/周榜内容，点标签原地换网格 | 1 层 | 视觉层级最少 | 滚动、分页、多数据源、空态复杂度最高，长列表体验差 |

推荐 **B**。它不是「零层级」，而是把今天散落在两个 Tab 的多套层级收敛成：

```
发现（分类 Tab）
  └─ 统一内容流（同一个页面壳，按来源换数据）
       └─ 作品详情 → 阅读器
```

「推荐本本」「每周必看」因为展示模型特殊，保留专用内容区，但入口和返回栈都在「发现」内部。

## 4. 推荐方案：发现中心（Discover Hub）

### 4.1 信息架构

```
底部 Tab
├─ 首页（只做消费流：关注 / 排行榜 / 随便看看）
├─ 发现（原「分类」）
│   ├─ 特色内容
│   │   ├─ 🔥 推荐本本 · 预览行（有内容才显示）
│   │   ├─ 每周必看 · 最新一期预览行
│   │   └─ [禁漫汉化组] [禁漫去码] [全彩化]   ← chips
│   ├─ 官方分类
│   │   └─ 顶级 chips + 选中大类的子分类 chips
│   └─ 官方标签
│       └─ 4 组固定标签墙
├─ 搜索
└─ 我的
```

### 4.2 页面线框

```
┌──────────────────────────────┐
│ 发现                          │
├──────────────────────────────┤
│ 特色内容                      │
│ 🔥 推荐本本            查看全部 │
│ [cover][cover][cover][cover]  │
│                               │
│ 每周必看 · 第 42 期    查看全部 │
│ [cover][cover][cover][cover]  │
│                               │
│ [禁漫汉化组] [禁漫去码] [全彩化] │
├──────────────────────────────┤
│ 分类          10 个 · 23 个子分类│
│ [最新A漫][同人][单本][短篇]...  │
│ [全部][汉化][日语][CG图集]...   │
├──────────────────────────────┤
│ 官方标签        4 组 · 47 个    │
│ 点击标签查看该标签下的作品       │
│ 主题A漫                       │
│ [剧情向][校园][纯爱]...         │
│ 角色 / 扮演                    │
│ [萝莉][御姐][熟女]...           │
│ ...                           │
└──────────────────────────────┘
```

- 三个区块独立加载、独立空态：推荐为空就整块隐藏；每周必看失败就显示一个可点重试的小入口，不阻塞分类和标签。
- 页面本身仍是单列 `verticalScroll`（与现在的分类页一致），不引入嵌套滚动网格。

### 4.3 统一内容流页（FeedScreen）

所有「分页检索型」入口共用一套页面壳：

```
┌──────────────────────────────┐
│ ← 同人 · 汉化                  │
├──────────────────────────────┤
│ [全部][汉化][日语][CG图集]...   │  ← 仅子分类存在时
│ [新到旧][最多喜欢][最多观看] | [全部][在读][读完]
├──────────────────────────────┤
│ 作品网格（2/3 列，随设置）       │
│                               │
├──────────────────────────────┤
│ 共 1,234 条    1 2 3 … 125 跳页 │
└──────────────────────────────┘
```

统一 `FeedSource`：

```kotlin
sealed interface FeedSource {
    data class Category(val slug: String, val title: String, val sub: String?) : FeedSource
    data class Tag(val tag: String) : FeedSource
    data class Channel(val id: String) : FeedSource
}
```

数据映射：

| FeedSource | 请求 | 说明 |
|---|---|---|
| `Category(slug, null)` | `JmRepository.browse(page, slug, sort)` | 顶级分类走 `/categories/filter` |
| `Category(slug, sub)` | `JmRepository.searchDimension(sub, page, sort, 0, slug)` | 子分类沿用现有「关键词 + c=」策略 |
| `Tag(tag)` | `JmRepository.searchDimension(tag, page, sort, 3)` | 标签维度 |
| `Channel(id)` | `JmRepository.channelFeed(id, page, sort)` | 频道关键词搜索 |

统一的 `FeedViewModel` 负责：分页、排序、阅读筛选、滚动位置恢复、错误重试。分类详情、标签页、频道页三份重复逻辑合并成一份。

### 4.4 路由与返回栈

把现在的平铺路由改成分类 Tab 的嵌套导航图：

```kotlin
navigation(startDestination = "category/hub", route = "category") {
    composable("category/hub") { DiscoverScreen(...) }

    // 分页检索型：统一入口
    composable("category/feed/category?slug={slug}&title={title}&sub={sub}") { ... }
    composable("category/feed/tag?tag={tag}") { ... }
    composable("category/feed/channel?id={id}") { ... }

    // 专用展示型
    composable("category/promote") { PromoteScreen(...) }
    composable("category/weekly") { WeeklyScreen(...) }
}
```

效果：

- 底部「发现」Tab 在 Feed 页仍然高亮（嵌套图的父路由命中 `hierarchy`）。
- 返回键回到发现页，并保留原来的滚动位置。
- 首页不再通过 `navigate("promote")` 等顶层路由进入这些页面。
- 作品详情、阅读器仍是全局路由，从 Feed 进入时返回 Feed。

### 4.5 首页调整

- 删除排行榜 Tab 上方的频道入口行（推荐本本/汉化组/去码/全彩化/每周必看）。
- 排行榜页只保留：榜单档位 chips + 「共 N 部」+ 网格。
- 可选：在排行榜标题右侧保留一个文字链接「发现更多 →」，点击调用 `navigate("category")` 切 Tab，**不压入新页面**。建议先不加，等发现中心上线后观察是否需要。

### 4.6 特殊内容区

**推荐本本**

- 发现页只取第一个非空 block 做预览（最多 6 个封面）。
- 点击封面 → 作品详情；「查看全部」→ `category/promote`。
- `/promote` 轮换且可能为空：空/失败时整块隐藏，不做骨架屏承诺。

**每周必看**

- 发现页取最新一期，展示期数标题 + 前若干个封面。
- 「查看全部」→ `category/weekly`，保留现有期数切换。
- 若后续需要分页，在 WeeklyViewModel 内补页码，不影响 FeedScreen。

### 4.7 缓存与请求策略

- 分类树：沿用进程内缓存，发现页只请求一次。
- 标签：固定词表，零请求。
- 推荐/每周：首次进入惰性加载，成功后进程内缓存；下拉刷新时再更新。
- 三个区块并行加载但分别渲染，任何一块失败都不阻塞其它区块。

## 5. 迁移步骤（每步可独立发版）

| 阶段 | 内容 | 风险 |
|---|---|---|
| P1 | 把首页频道行搬到分类 Tab 顶部，首页只留榜单；详情仍用旧路由 | 低 |
| P2 | 分类/标签/频道路由收进 `navigation("category")` 嵌套图，修正底部 Tab 高亮与返回 | 中 |
| P3 | 引入 `FeedSource` + 统一 `FeedScreen/FeedViewModel`，替换三套重复页面 | 中 |
| P4 | 发现页加推荐/每周预览 + 「查看全部」；空态、缓存、埋点与体验收尾 | 低 |

每阶段都用模拟器回归：

- 首页排行榜无频道行；
- 发现页三个区块都能进入内容；
- 从 Feed 返回发现页滚动位置不丢；
- 底部 Tab 在 Feed 页保持高亮；
- 详情页标签点击进入标签 Feed；
- 推荐/每周为空时页面不出现空白区块或报错。

## 7. 待定的产品决策

1. **底部 Tab 名称**：继续叫「分类」，还是改为「发现」？
   建议改「发现」——合并后它同时承载推荐、每周必看、频道、分类和标签，「分类」已经名不副实。
2. **首页是否保留一个「发现更多」文字入口**：
   建议先不加；发现中心的内容位本身足够强，避免又制造第二个前门。
3. **推荐本本在发现页的排序位置**：
   建议放在特色内容第一块但只有非空时显示；如果运营内容质量不稳定，可降到频道 chips 下方甚至默认折叠。
4. **每周必看是否需要分页**：
   当前只取第 1 页。若上游存在更多页且内容量足够，再补分页；本次不扩大范围。
