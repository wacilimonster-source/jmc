# JM Reader · 统一书架（收藏 × 历史合并）产品设计

> 需求来源：用户指出「云端收藏 / 云端历史 / 本地书架 / 阅读历史」四功能重复，要求合并为单一入口，
> 收藏与阅读动作实时同步，入口内不区分数据来自本地还是云端。
> 基线：v0.2.1（b6f79d4）。本文档取代 product-design.md §5.6 与 §5.9 中关于四个入口的描述。
> 版本：v1.0 · 2026-10-31

---

## 0. 一页纸结论

- **判断属实**：四个功能是同一个 2×2 矩阵——{收藏, 历史} × {本地, 云端}，语义各重复一次，且登录态把两对各自割裂。
- **方案**：四入口合并为一个**「书架」**，数据 = `收藏 ∪ 阅读历史` 的并集视图；UI 内**不出现任何来源标记**（本地/云端），只保留用户动作状态（是否收藏、是否读完、续读进度）。
- **收藏 = 双写**：心形操作永远先写本地（即时生效、离线可用）；已登录则异步推送云端翻转，失败入**同步队列**，按「对账补差」重试（不盲目重发——翻转端点非幂等）。
- **历史 = 本地为主、云端只读导入**：`/watch_list` 无写入端点（调研确认），本地进度永远优先；云端历史仅作为「别处读过」的条目并入列表，排序上参与「最近动态」。
- **可做，且改动面可控**：现有四个存储（Bookmarks / RecentReads / progress / 云端两列表接口）全部不动，新增一个合成层 + 同步队列；删的是 3 个页面和 2 个菜单行，不是数据迁移。

## 1. 问题定义：四个功能为什么重复

### 1.1 现状矩阵

| | 收藏（我想存） | 历史（我读过） |
|---|---|---|
| **本地** | 本地书架 `Bookmarks`（DataStore JSON） | 阅读历史 `RecentReads`（最多 100 条）+ 章节/页进度 |
| **云端** | 云端收藏 `GET /favorite`（可读写） | 云端历史 `GET /watch_list`（只读） |

四格在产品语义上只有两行：**「收藏」**和**「历史」**。列（本地/云端）本应是实现细节，现在却被当成了四个产品功能。

### 1.2 割裂的具体表现（代码事实）

1. **心形按登录态二选一**（`ComicDetailViewModel.favourite()`）：
   登录 → 只翻转云端收藏；未登录 → 只写本地书架。同一个动作、同一颗心，落进两个互不相通的存储。
   - 登录用户：收藏永远不进本地书架 → **断网/退出登录后书架全空**，离线收藏能力形同虚设。
   - 先未登录收藏、后登录的用户：本地书架有一堆，云端收藏是空的，两者还各自显示「已收藏」。
2. **两个收藏列表可能同时含有同一本**，互不知道对方的存在；详情页心形初值只看 `本地 ∪ 云端id缓存` 的拼接，状态解释成本高。
3. **两条历史平行展示**：同一本漫画在「阅读历史」里有精确到页的续读进度，在「云端历史」里又是一条裸条目；product-design.md 甚至明确写了「两者不合并展示」——本设计推翻这一条。
4. **我的页菜单 8 行里 4 行是漫画列表**（云端收藏 / 云端历史 / 本地书架 / 阅读历史），信息架构被实现结构牵着走。

### 1.3 云端能力的边界（设计前提，全部来自实测/调研）

| 能力 | 状态 | 依据 |
|---|---|---|
| 云端收藏读 | ✅ `GET /favorite`，条目带 `latest_ep`（有更新角标数据源） | `JmCapabilities.hasCloudFavouriteRead = true` |
| 云端收藏写 | ✅ `POST /favorite {aid}` **翻转端点**，响应 `type=add\|remove` | `hasCloudFavouriteWrite = true`（2026-09-25 实测） |
| 云端历史读 | ✅ `GET /watch_list` | `hasCloudHistory = true` |
| 云端历史写 | ❌ 调研未发现任何 push/删除端点 | research-jm-protocol.md |
| 翻转端点幂等性 | ❌ 非幂等：连调两次 = 加了又取消 | 端点语义本身 |
| `/favorite` 高频风险 | 高频连续请求会 401 | JmRepository 代码注释实测 |

**两个硬约束直接决定同步架构**：
- 翻转端点非幂等 ⇒ **不能**「失败就重发」；只能先对账（拉云端 id 集合）再补差。
- 云端历史无写入 ⇒ 「阅读后云端历史同步更新」对 **云端** 无从谈起，只能诚实做成只读导入；本地进度是唯一权威。

## 2. 目标与非目标

### 目标

1. **一个入口**：我的页四个列表入口收敛为一个「书架」。
2. **一次动作，处处生效**：心形 = 本地 + 云端双写；阅读 = 本地进度即时记录并反映到书架排序。
3. **入口内无来源感**：列表是并集，不显示「本地」「云端」字样或角标；用户感知到的维度只有：是否收藏、是否读完、续读进度、有更新。
4. **离线与未登录完整可用**：延续「未登录 ≠ 残缺」，云端部分缺席时书架照常用。
5. **收藏态全局一致**：详情页、书架卡片、列表角标的心形永远指向同一个真相。

### 非目标（本期不做）

- 不做评论/下载/作者的云端化（与本次无关）。
- 不做多设备冲突解决 UI（以简单规则裁定，见 §4.4）。
- 不做云端历史的删除/清空（无端点，能力位 `false`，入口不出现）。
- 不改「收藏的作者」「关注管理」（不同领域，不在此矩阵内）。

## 3. 核心概念重定义

| 概念 | 新定义 |
|---|---|
| **书架（Library）** | `本地收藏 ∪ 云端收藏 ∪ 本地阅读历史 ∪ 云端历史` 按漫画 id 去重后的统一列表。唯一入口。 |
| **收藏（collect）** | 一个用户动作，双写：本地书架（权威、即时）+ 云端收藏（尽力送达、可排队）。卡片心形实/空 = 该状态。 |
| **阅读记录（history）** | 本地进度（章节+页+时间戳）永远记录；云端历史只读并入。有进度即可「续读」。 |
| **最近动态（排序键）** | `max(收藏时间, 本地最后阅读时间, 云端最后阅读时间)`，书架默认排序。 |

### 3.1 条目状态模型（UI 唯一消费的形状）

```
LibraryItem {
  comicId, title, author, coverUrl
  collected: Boolean          // 心形（= 本地书架含 或 云端收藏含）
  collectedAt: Long?          // 收藏时间（本地优先，云端次之）
  lastReadAt: Long?           // max(本地 ts, 云端时间)
  progress: (order, page)?    // 仅本地有；云端-only 条目为 null
  finished: Boolean           // ReaderStatus.FINISHED
  hasUpdate: Boolean          // 仅云端收藏条目的 latest_ep 可判时为 true，否则恒 false（不伪造）
}
```

## 4. 数据与同步设计

### 4.1 分层：现有存储全部不动，新增一个合成层

```
┌─ UI：LibraryScreen / LibraryViewModel ──────────────────────────┐
│                                                                  │
├─ 新增 LibraryRepository（合成层，内存态 + TTL 缓存）──────────────┤
│   merge(Bookmarks.items, ReaderPrefs.recentReads(),             │
│         cloudFavourites*, cloudHistory*, ReaderStatus,          │
│         SyncQueue.pending)  → List<LibraryItem>                 │
├─ 新增 FavouriteSyncQueue（DataStore 持久化待同步队列）────────────┤
├─ 现有 Bookmarks / ReaderPrefs / ReaderStatus（不改结构）─────────┤
├─ 现有 JmRepository.favourites / cloudHistory / favourite ───────┤
└──────────────────────────────────────────────────────────────────┘
```

- `Bookmarks`、`ReaderPrefs`（进度/历史/读完）、`ReaderStatus` 结构零改动 → **存量用户数据天然迁移**，无升级脚本。
- 云端两列表仅在已登录时参与合并，拉取失败不阻塞本地部分。

### 4.2 收藏双写规则（心形）

**写入顺序（点击后 200ms 内全部发生）：**

1. **本地先行**：`Bookmarks.toggle()` 同步执行 → 收藏态立即生效（离线也成功）。
2. **云端尽力**：若已登录且 `hasCloudFavouriteWrite`，异步调用 `JmRepository.favourite(id)`：
   - 成功：以响应 `type=add|remove` 校准本地心形展示，作废 `favIdsCache`。
   - 失败（网络/401/超时）：本地收藏态**保持不变**，向队列插入一条 `{comicId, 意图: add|remove, ts}`，Toast「已收藏，云端同步稍后自动完成」。
3. **防抖**：沿用现有 `togglingFavourite` 在途锁；队列 flush 期间该 id 的新意图直接覆盖旧意图（同 id 只保留最新意图——翻转端点下这是唯一安全的合并方式）。

**队列对账（flush）——绝不盲目重发翻转：**

```
flush 时机：App 启动(已登录) / 登录成功 / 书架进入下拉刷新 / 任意云 API 成功后惰性触发
flush 步骤：
  1. cloudIds = cloudFavouriteIds(force=true)   // 以列表为准的真相
  2. 对每条 pending {id, 意图}：
       意图=add    且 id ∉ cloudIds → 调 favourite(id)，校验响应 type==add
       意图=remove 且 id ∈ cloudIds → 调 favourite(id)，校验响应 type==remove
       已符合预期 → 直接出队（零请求）
  3. 全部成功 → 清队列 + LogStore 记录；任一失败 → 保留剩余，下次再试
```

- 对账前置的 `cloudFavouriteIds(force)` 保证：即使 App 断网 3 天、用户在官方 App 里手动取消过收藏，我们也不会把过期意图翻到错误方向。
- 队列串行、条间不加人为延迟（现网 401 风险来自高频列表请求，队列量级是个位数）。
- 队列持久化在 DataStore（与 Bookmarks 同模式），杀进程不丢。

**未登录**：只写本地。队列机制对未登录用户完全不激活（不积累、不提示）。

### 4.3 登录时刻的一次性合并（backfill）

用户从「纯本地」走向「登录」的那一刻，两个收藏世界首次见面：

- **检测**：登录成功后，若本地书架非空且 `cloudIds` 中缺失其中的条目 ≥ 1，弹一次性确认对话框：
  > 「把本地书架的 N 本同步到云端收藏？同步后换设备、官方 App 里都能看到。」
  > [同步到云端] [暂不]
- 「同步到云端」→ 逐条走 `favourite(id)`（意图=add，复用 4.2 队列与对账，天然幂等安全），完成后 Snackbar 汇报「已同步 N 本，M 本失败可在书架重试」。
- 「暂不」→ 写入 `SourcePrefs.backfillDeclined = true`，**不再二次打扰**；设置页提供「把本地书架同步到云端」手动入口兜底。
- 方向只做 **本地 → 云端**。云端 → 本地的反向灌入不做：云端收藏经 4.4 的并集规则已经出现在书架里，复制进本地存储只会制造第二份真相。
- 该对话框每个账号生命周期内最多出现一次（以 uid 记），不随登出/重登循环出现。

### 4.4 阅读历史的合并规则

| 情形 | 行为 |
|---|---|
| 仅本地有进度 | 正常条目，续读「第 N 话 P 页」，`lastReadAt` = 本地 ts |
| 本地 + 云端都有 | **同一条目**。续读用本地进度（精确到页，永远优先）；`lastReadAt` = 两者最大值；不展示两份 |
| 仅云端有（在官方 App/网页读过，本 App 从未打开） | 并入列表，无续读行；点卡片进详情页，由详情页正常发起阅读，此后转为「本地+云端」 |
| 读完后（`FINISHED`） | 状态行「已读完」；排序仍按 lastReadAt 参与最近动态 |

- **取消收藏 ≠ 清除历史**：心形只动收藏（本地书架 + 云端），不动进度与历史条目；清除历史是独立菜单项（见 §5.3）。
- 本地历史容量维持现状（100 条滚动窗口）；云端历史按页懒加载，见 §5.4。

### 4.5 退出登录

- 云端收藏/历史条目自然从书架消失（账号资产随账号走），本地条目原样保留——这是预期行为，不做「登出留副本」。
- 登出前若有未 flush 的同步队列：队列保留在磁盘（含意图），下次登录自动续传。**风险声明**：意图基于登出前的真相生成，重登后 flush 的对账步骤（拉 force 云端集合）天然纠偏，不会翻错。

## 5. UI 设计

### 5.1 信息架构变化

**我的页**（8 行 → 6 行）：

```
删除：云端收藏 / 云端历史 / 本地书架 / 阅读历史        （4 行）
新增：书架    （1 行，副标题显示「N 本收藏 · M 本在读」）
保留：收藏的作者 / 关注管理 / 下载 / 设置 / (退出登录)
```

- 「书架」排到菜单第一位，登录后紧跟账号卡片（高频入口上移）。
- 路由：新增 `library`；删除 `bookmarks` / `recent-reads` / `cloud-favourites` / `cloud-history` 四条 composable（页面文件物理删除，不留死代码）。
- 全局其它引用点同步收敛：阅读器退出/详情页「继续阅读」等既有跳转不变；列表角标读取处改查 `LibraryRepository`（或直接沿用 Bookmarks/ReaderStatus 现有读取——它们仍在）。

### 5.2 书架页结构

```
┌──────────────────────────────────────────┐
│ 书架                          [排序▾]     │  ← 顶栏
│ (全部) (收藏) (在读) (读完)               │  ← 状态 chips，单选，默认「全部」
│ ┌────┐ 标题                               │
│ │封面│ 作者 / 状态行                        │  ← 卡片
│ └────┘ [♥]                               │  ← 右下角心形（实/空）
│ …                                        │
│ 顶部可下拉刷新；触底懒加载云端续页            │
└──────────────────────────────────────────┘
```

- **chips 是状态维度不是来源维度**（对齐「不区分本地云端」）：
  - 全部 = 并集全集
  - 收藏 = `collected == true`
  - 在读 = 有进度且未 `finished`
  - 读完 = `finished == true`
- **卡片状态行**（一行文本，优先级从上到下取第一个命中）：
  1. 「续读 · 第 N 话 P 页」（有本地进度且未读完）——点卡片直接进阅读器续读，与现有最近阅读一致
  2. 「已读完」
  3. 「有更新」（`hasUpdate`，金色角标）
  4. 空白（纯收藏未读 / 云端-only 条目）
- **卡片心形**：点击 = 与详情页同一套双写逻辑；history-only 条目空心，一点即收藏。
- **默认排序**：最近动态（§3）。排序菜单仅两项：最近动态 / 收藏时间——云端 `o=mp` 的「按更新时间」不再暴露（并集后语义不成立，能力说真话）。

### 5.3 长按菜单（卡片级）

| 菜单项 | 行为 |
|---|---|
| 收藏 / 取消收藏 | 双写切换（同 §4.2） |
| 清除阅读记录 | 只删本地历史与进度（`RecentReads` + progress + ReaderStatus 降级）；**收藏不动**；云端历史无法删（无端点），菜单里不出现「清空云端历史」字样 |
| 下载整本 | 跳现有下载管理流程 |
| 打开详情 | 常规跳转 |

- 现有「长按封面移出书架」「删除阅读历史 + Snackbar 撤销」交互全部迁入此菜单语义；撤销仅覆盖本地删除。
- 清除阅读记录需二次确认（沿用现有 AlertDialog 文案样式）。

### 5.4 分页与数据加载

- 首屏 = 本地全量（书架 + 历史都在内存）∪ 云端收藏第 1 页 ∪ 云端历史第 1 页，**目标与现云端收藏页首屏耗时持平**。
- 触底懒加载：云端两个列表各自按页续拉，新页合并进并集（按 id 去重后追加/前插视排序键）。加载更多失败显示底部重试行，不影响已合并内容。
- 下拉刷新：force 重拉云端两列表第 1 页 + 触发同步队列 flush。
- 云端仅在已登录时拉取；未登录首屏就是纯本地，零请求。

### 5.5 空态与错误态

| 状态 | 表现 |
|---|---|
| 书架空（无收藏无历史） | 插图 + 「书架还是空的」+「去首页逛逛」按钮 |
| 收藏 chip 空 | 「还没有收藏，看到喜欢的本子点亮 ♥ 吧」 |
| 在读/读完 chip 空 | 一句话空态，无按钮 |
| 云端拉取失败（已登录） | **顶部错误条**（沿用首页断服样式）：「云端数据同步失败，当前显示本地内容」+ [重试]；本地部分正常可操作 |
| 队列有积压 | 书架顶栏下细提示行：「N 条收藏变更待同步」，点击立即 flush |

### 5.6 详情页与阅读器联动

- 详情页心形：改走 §4.2 双写（行为变化：**登录用户也会落本地书架**）；心形初值 = `collected`（本地 ∪ 云端缓存），与现状取值一致。
- 阅读器退出存进度（现状已有）→ 书架状态行与排序自动反映（StateFlow 驱动重组，无需手动刷新）。
- 「我的页」账号卡片下说明文案更新：未登录 = 「收藏与历史保存在本机，登录后同步到云端」。

## 6. 待实测探针（开发前 20 分钟）

| # | 探针 | 影响的决策 | 两种结果的处理 |
|---|---|---|---|
| P0 | 带 AVS 会话调 `GET /album?id=`（从未读过的本子）→ 立即查 `GET /watch_list`，确认是否自动入云端历史 | 「阅读后云端历史是否自动更新」的解释口径 | 入了：文案与文档声明「阅读自动计入云端历史」；没入：按本文档口径「云端历史仅镜像官方平台记录」，UI 无差异 |
| P1 | 同一 id 连续两次 `POST /favorite` 的响应时间与 401 行为（间隔 1s / 3s） | 队列 flush 的节流参数 | 无 401：不节流；有：条间 3s 串行 |
| P2 | `/watch_list` 条目字段里是否有可用的「最后阅读时间」（当前 `toSummary()` 是否丢弃了时间字段） | 云端-only 条目的排序值 | 有：用之；无：云端-only 条目排序值取列表位次*页大小近似，仅保证不 crash、顺序大致正确 |

P0/P1 用 tools/ 现有 jm-api-check 脚手架加两个 case 即可；P2 看 DTO 现有字段。

## 8. 验收标准（真机 checklist）

| 场景 | 必查项 |
|---|---|
| 未登录收藏 | 心形 → 本地书架有；书架页可见可续读；全程无网络请求报错 |
| 未登录阅读 | 打开阅读器 → 书架「在读」chip 出现，状态行「续读 · 第 N 话 P 页」正确 |
| 登录后收藏 | 心形 → 云端收藏列表（网页/官方 App 交叉验证）**且**本地书架都有；两端状态一致 |
| 离线收藏（已登录） | 断网点心形 → 本地立即生效 + 「云端同步稍后自动完成」提示；恢复网络 → 不操作 App，1 分钟内云端出现该书 |
| 翻转安全 | 断网时收藏 + 取消收藏连续操作 → 恢复后云端最终态 = 本地最终态（不出现反向） |
| 登录 backfill | 本地有 3 本、云端空 → 登录弹确认 → 同步后云端 3 本；选「暂不」→ 不再弹，设置页手动入口可用 |
| 云端-only 条目 | 官方 App 里收藏/读一本 → 本 App 书架出现（刷新后），无续读行；点进详情正常 |
| 进度优先级 | 本地读到第 3 话、云端记录在第 1 话 → 续读直达第 3 话 |
| 取消收藏 | 书架卡片取消 → 云端收藏同步消失（交叉验证）；阅读记录与进度保留 |
| 清除阅读记录 | 条目从书架消失（未收藏时）/ 心形保留（已收藏时）；Snackbar 撤销有效 |
| 退出登录 | 云端-only 条目消失，本地条目不动；重登后云端条目回来、积压队列自动续传 |
| 断服 | 手填坏域名 → 书架显示本地内容 + 顶部错误条；换线路恢复 → 下拉刷新合并云端 |
| 双 App 隔离 | 与 PiKA 互不影响（数据目录独立，天然满足，列此项防回归） |
| 性能 | 书架首屏耗时 ≤ 现云端收藏页首屏 +10%；100 条本地历史滚动无卡顿 |

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 翻转端点被重试翻错方向 | 队列只存**意图**不重放请求；flush 前强制对账 `cloudFavouriteIds(force)`；同 id 意图合并只留最新 |
| `/favorite` 高频 401（实测存在） | 队列量级个位数 + 串行 + P1 探针定节流；favIdsCache 机制沿用 |
| 并集列表首屏变慢 | 本地全量在内存、云端仅各 1 页；懒加载续页；首屏预算见 §8 |
| DataStore JSON 全量重写放大（书架条目变多） | Bookmarks/队列条目量级 ≤ 数百，现状模式已验证；不引入 Room，不为本次改存储引擎 |
| 登录 backfill 误写云端（写侧谨慎原则） | 一次性确认对话框 + uid 级记忆 + 手动入口兜底；不静默批量写 |
| 云端历史被用户误认为可删除 | 「清除阅读记录」文案明确「仅清除本机记录」；无云端删除入口（能力说真话） |
| 心形语义变更冲击老用户（登录用户从「只云端」变「双写」） | 行为增强而非破坏：云端照写；新增的本地副本正是用户在断网/登出场景期待的行为；更新说明写进 release notes |
