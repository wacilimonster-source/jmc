## 1. 确认缺陷（P0/P1，必须修）

### A. 收藏 / 账号数据安全

1. **[P0] 云端收藏 id 集合可能返回“半截”并被当作权威，导致反向取消收藏**
   `core/JmRepository.kt:424-445` + `core/library/LibraryRepository.kt:196-213`
   `cloudFavouriteIds()` 最多拉 3 页，任一页失败即 `break`，但仍返回已收集的部分 id。调用方 `setCollected()` 把“不在集合里”当成“云端未收藏”，对翻转端点发一次请求；对实际已收藏但落在未拉取页的作品，会把收藏**取消掉**并同步删本地书架。3 页上限（旧实现按 80/页=240 本）与真实页大小不符后更容易触发。

2. **[P1] `/favorite` 真实页大小是 20，代码按 80 计算**
   `core/JmRepository.kt:409-412,558`
   线上抓包：`list[20] / count=20 / total="26"`。`pagesOf(26,20,1,80)` 推得 1 页，第 2 页 6 本永远不显示；首页缓存捷径还把前 20 本当作完整集合缓存 5 分钟。同一问题存在于 `cloudFavouriteIds()` 的翻页终止判断。

3. **[P1] `/watch_list` 真实页大小也是 20，代码按 80 计算**
   `core/JmRepository.kt:507`
   线上抓包：`list[20] / total=20`。历史超过 80 条时页数被低估，云端历史被截断。

4. **[P1] 收藏翻转 POST 在传输失败后会被自动重试，可能翻转两次**
   `network/JmClient.kt:124-190`
   `execute()` 的换域重试对 POST 同样生效。若服务端已处理 `/favorite` 但响应丢失（读超时/连接重置），重试会再翻转一次，用户“收藏”变“取消”。

5. **[P1] 显式退出后 401 钩子会把用户静默重新登录**
   `core/JmRepository.kt:89-114` + `core/JmRepository.kt:128-133`
   401 钩子不检查当前是否仍处于登录态；退出时若仍有在途请求返回 401（典型是自动签到），钩子会读取已保存凭据重新 `/login`。同时重登失败（含网络错误/协程取消）会无条件 `clearJmLogin()`，把可恢复的断网变成强制登出。

6. **[P1] 收藏同步队列无并发保护，flush 可能删掉更新的用户意图 / 并发翻转两次**
   `data/FavouriteSyncQueue.kt:61-149`
   `enqueue()` 与 `flush()` 的 `remove()` 无互斥；flush 期间用户再次点击会写入新意图，旧 flush 完成后按 comicId 无条件删除，新意图丢失。两个 flush 并发（启动 + 书架刷新）会对同一 id 各发一次翻转。

7. **[P1] 收藏同步队列不区分账号**
   `data/FavouriteSyncQueue.kt:28-34` + `core/library/LibraryRepository.kt:222-229`
   队列条目没有账号标识，退出 A 登录 B 后启动 flush 会把 A 的意图作用到 B 的云端账号。

8. **[P1] 本地书架读改写无同步，异步落盘可能乱序**
   `data/Bookmarks.kt:71-99`
   `add/remove` 直接读 `_items.value` 再写回；两个并发收藏（不同漫画、书架/详情同时操作）会丢其中一条。`persist` 每次独立 `AppScope.launch` 写 DataStore，旧快照可能后落盘覆盖新快照。

9. **[P1] 书架卡片收藏没有在途保护，快速双击会“加了又取消”**
   `ui/library/LibraryScreen.kt:97-108`
   详情页有 `togglingFavourite` 防抖，书架卡片没有；两次点击读到同一个旧状态，各发一次翻转。

10. **[P1] 取消云端收藏后 `_cloud.favourites` 不更新，心形残留且无法再次收藏**
    `core/library/LibraryRepository.kt:180-214` + `core/library/LibraryModels.kt:88-97`
    `LibraryMerge` 把云端收藏强制标成 `collected=true`。取消收藏成功后该条目仍留在云端收藏列表里，心形保持点亮；再次点击目标态仍是 false，成为永久空操作。

### B. 签到 / 分页 / 解析

11. **[P1] 自动签到永远显示“今日已签到”**
    `core/JmRepository.kt:497`
    判据只比较日期是否存在，不检查 `signed`。月历矩阵本来就会包含今天（未签），所以 `checkIn()` 永远提前返回，`/daily_chk` 从不调用；`DailyCheckIn` 还把今天记为成功。

12. **[P1] 评论页大小按 20 计算，真实是 10，长评论区后半段不可达**
    `core/JmRepository.kt:391,559`
    fixture `/forum`：`list` 10 条、`total=1075`。`pagesOf(1075,10,1,20)` 推得 54 页，实际 108 页。

13. **[P1] 浏览流把 10000 哨兵传给 `pagesOf`，小分类永远到不了底**
    `core/JmRepository.kt:182`
    注释与 `PagesOfTest` 都约定浏览流传 `total=0`（按当页条数判断），实现传了 `data.data.total`（恒 10000），于是固定推得 125 页。少于 80 条的分类会继续请求空页直到第 125 页。

14. **[P1] 多词搜索可能陷入无限网络重试**
    `ui/search/SearchViewModel.kt:288-311`
    阶段 2 的 `madeProgress` 只看“还有未访问页”，而 `wordProgress` 只在返回非空时推进。某页持续失败或合法返回空页时，同一页会被无限请求，`_multiLoading` 永不结束，离开页面后仍继续。

15. **[P1] 搜索筛选分页按 20 条切片，但页码仍按服务端 80 条计算**
    `ui/search/SearchScreen.kt:249-259,359-366` + `ui/search/SearchViewModel.kt:437-439`
    50 条结果时 `totalPages=1`，筛选只能看到前 20 条；更大结果集只可达 `totalPages×20` 条。切换筛选时还把 VM 的服务端页码重置为 1，导致后台补页重复追加已加载页。

16. **[P1] 分类详情筛选模式从不加载更多页**
    `ui/category/CategoryScreen.kt:378-396,461-477`
    筛选只对单页数据切片；没有搜索页那样的后台补页 effect，`onLoadMore = {}`，`BrowseViewModel.loadMore()` 从未被调用。

17. **[P1] 搜索/分类“加载更多”失败被当成到底**
    `ui/search/SearchViewModel.kt:425-430` + `ui/category/CategoryScreen.kt` 同等路径
    失败只置 `_endReached=true`，不写 `_searchError`；用户看到“到底了”或半截列表，没有重试入口。

### C. 阅读器

18. **[P1] 切章时旧协程可能在新章之后发布旧页**
    `ui/reader/ReaderViewModel.kt:136-198`
    `loadJob?.cancel()` 是协作式取消；旧任务在网络返回后到写 `_pages` 之间没有挂起点/代际检查，可能在新章页面发布后覆盖 `_pages` 与恢复页，造成“新章标题 + 旧章图片”以及进度写错章节。

19. **[P1] 离线/部分页场景会把作品误标为“已读完”**
    `ui/reader/ReaderViewModel.kt:416-421`
    `saveProgress()` 用 `_chapters.value.maxOfOrNull { it.order }` 判断最后一章；目录请求失败时 `_chapters` 是“已下载章节兜底列表”（例如 100 话只下载了 3 话），读到第 3 话末页就会 `saveFinished`。

20. **[P1] 坏图片磁盘缓存永远无法通过“点击重试”恢复**
    `core/scramble/JmImageFetcher.kt:104-136` + `CoilImageInterceptors.kt:63-68`
    Fetcher 无条件先读自定义磁盘缓存，忽略 `options.diskCachePolicy`；`#retryN` 又被刻意排除在缓存键外。CDN 返回 200 的 HTML/半截图一旦落盘，之后每次重试（包括管线级 WRITE_ONLY 重试）都命中同一份坏字节，只能清缓存。

21. **[P1] 滚动流把图片放大到 2160×高度上限，内存峰值翻倍**
    `ui/reader/WebtoonSplitPage.kt:93-103` + `ReaderViewModel.preloadNearby`
    请求显式指定 `Size(2160, cap)`，Coil 默认 `Precision.AUTOMATIC` 在显式 Size 下 `allowInexactSize=false`，会把小于目标的图**放大**（例如 960×1355 → 2160×3049，约 26MB ARGB）。预取还用了另一套尺寸，导致重复解码。

22. **[P1] 预取请求从不释放，且低内存分支提前 return**
    `ui/reader/ReaderViewModel.kt:89-90,503-534`
    `preloadDisposables` 没有在 `onCleared()` 释放；`MemoryBudget.shouldDisablePrefetch()` 为 true 时直接返回，上一窗口的在途预取继续跑。预取 effect 的 key 不含章节，切到相同页码的新章不会取消旧章预取。

### D. 下载

23. **[P1] 下载成功判定不校验响应内容/页数**
    `core/download/DownloadManager.kt:693-714,596-610`
    任意 2xx 响应都会落盘；CDN 风控页/空响应可被当成页面。章节接口返回空列表时 `pageCount=0` 仍标记 COMPLETED，离线阅读打开是空白/缺页。

24. **[P1] `isDownloaded()` 对 COMPLETED 不验证文件**
    `core/download/DownloadManager.kt:178-188`
    文件被清理/损坏但清单仍是 COMPLETED 时，详情页显示已下载、整本下载跳过该章，阅读器走“本地完整”分支后不回落网络。

25. **[P1] 恢复下载清单后不落盘合并结果**
    `core/download/DownloadManager.kt:746-773`
    `restoreTasks()` 在锁外扫描目录，锁内合并后没有 `persist()`；期间任意 enqueue/retry 会用未合并的列表覆盖清单，进程被杀后旧任务永久丢失。

## 3. 复核中确认的“不是缺陷”

| 候选 | 结论 |
|---|---|
| 阅读器 `pointerInput(Unit)` 捕获过期 `pages/scrollMode`，首次触摸早于加载会永久失效 | **误报**。`pages`/`scrollMode` 是 Compose 委托状态，lambda 内每次调用都经 State 读取实时值；`rowPrefix` 也是 `derivedStateOf` 委托。不存在首次触摸冻结。 |
| Webtoon 解码“封顶”实际会放大小图 | 真实缺陷（已列入 #21），通过 Coil 2.7 字节码确认 `Precision.AUTOMATIC` + 显式 Size 时 `allowInexactSize=false`，`computeSizeMultiplier` 可 >1。 |
| `restoreTasks()` 合并后不落盘 | 真实（#25）。 |
| 分页类问题 | 全部用线上抓包/fixture 复核，页大小分别是：浏览/搜索 80、收藏 20、云端历史 20、评论 10。 |

## 4. 暂缓项（风险/收益比本次发版不合适）

| 项 | 原因 |
|---|---|
| `WebtoonSliceCache` 以 `ref#order` 为键，目录重排后切片数可能串章 | 需要把稳定 chapterId 贯通到测量回调，改动面较大；重排时已有 `LaunchedEffect(vmOrder, pages.size)` 清空并重载缓存，实际影响窗口很小。 |
| 图片下载使用阻塞 OkHttp，协程取消不能中断 `Call` | 需要把 `fetchJmImageOnce` 改成 `suspendCancellableCoroutine` + `call.cancel()`；本次先通过预取释放/尺寸修正降低在途请求量，列入下一版。 |
| 恢复定位 3 秒窗口期间抑制保存 | #36 只修“退出/切后台不丢新位置”的低风险部分；完整改成按滚动事件消费恢复页需要重构恢复状态机。 |
| 关注流多目标局部失败 | #59/#60 先补错误计数与不静默丢页；按目标合并旧数据需要重做 feed 缓存模型。 |
